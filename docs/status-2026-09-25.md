# Khapee — where everything stands

25 September 2026. Covers the Petpooja integration, Khapee's own billing,
notifications, and what makes menu data permanent. Each section says what
works, what is left, who is blocking it, and what to do instead if it does not
come through.

---

## 1. Petpooja

### Working

- All ten endpoints: `save_order`, `update_order_status`, `mapped_restaurant_menus`
  outbound; menu push, `item_stock`, `get_store_status`, `update_store_status`,
  `callback` inbound.
- Menu push applies items, categories, prices (rupees → paise), the veg flag
  and sold-out state. A dish dropped from a payload is taken **off the menu,
  never deleted**.
- **Tables come from the menu push**, which is where Petpooja said they live.
  `table_no` now sends their name and falls back to ours.
- **A round is what gets sent, not the order.** Their API is one KOT per order;
  ours accumulates rounds all evening. Each round goes over as its own order
  against the same table, with a `-2`/`-3` suffix so their duplicate check
  passes, and the callback strips the suffix again.
- Their Accept lands on the customer's tick, mapped per service mode.
- Webhook secret auth, with payloads naming another restaurant rejected.

968 tests pass, four of them new for tables.

### Left

| What | Who is blocking |
|---|---|
| `app_key`, `app_secret`, `access_token` | **Petpooja.** `linkReady()` gates every call — nothing fires without all three |
| `PETPOOJA_BASE_URL` | **Petpooja.** Unset means we talk to their staging, deliberately |
| Registering our five webhook URLs on their side | **Petpooja** |
| `payment_type` — we send `ONLINE`, their reply listed only Cash, Card, COD, Other | **Unanswered question.** Risk: a customer asked to pay twice |
| Tax is sent as `0.00` | Us. `tax.ts` computes GST properly; none of it reaches the payload |
| `menusharing_code` stored but never used | Us, small |
| "Sync now" rides the deprecated Fetch Menu API | Us, low priority |

### If Petpooja never comes through

**Khapee does not need them.** It already prints its own KOTs and bills:
`floor.ts` has rounds, `tableBill` and `settleTable`; `receipt.ts` does
one-click printing, self-printing from an iframe with a visible-window
fallback. The integration is an optimisation for kitchens that already run
Petpooja, not a dependency. Restaurants can be onboarded today without it.

### If a push fails mid-service

By design, nothing blocks: the order lives in Khapee, `pos_error` is written on
the order and `last_error` on the link, and the dashboard shows both. A till
that is switched off cannot stop a customer ordering.

## 2. Khapee's own billing

### Working

Immutable invoices that copy dish names, prices, tax rates, HSN codes and who
the restaurant legally was — edit the menu tomorrow and last night's bill still
reads the same. Per-financial-year numbering taken inside the transaction.
Idempotent: a cashier tapping twice gets the first invoice, not a second
number. Split payments, and voids that never reuse a number.

### Broken — the one worth fixing first

Two settlement paths exist and they are not connected:

- `POST /staff/orders/:id/invoice` → `finaliseInvoice()` → a proper numbered
  GST invoice.
- `POST /staff/floor/table/:id/settle` → `settleTable()` → writes payments,
  flips `payment_status` to PAID, sets `bill_closed_at`, and **never touches
  `invoice_id` or calls `finaliseInvoice`**.

The dine-in path — the one the whole floor screen is built around — takes the
money and produces **no tax invoice at all**. For a GST-registered restaurant
that is a compliance hole rather than a cosmetic one.

### Until it is fixed

Bill each order individually through the per-order invoice route, which works
correctly. Clumsy across a table that ordered four times, but it is legal
paper.

## 3. Notifications

### Fixed

- **Every restaurant.** The grant could never be given: `all_restaurants` was
  honoured when sending and accepted when saving, but no route ever set it —
  and the dashboard re-subscribes on every page load with the flag defaulting
  to false, so even an invite that set it was cleared by the next reload. It is
  now decided from the account on every subscribe.
- **Every order.** A friend adding a round to an open table wrote only the row
  the dashboard reads, and the dashboard is shut for most of a service. Later
  rounds now push and email like a first order, with wording of their own.
- A waiter adding items stays silent on purpose — they just typed it in.

### Left — all configuration, no code

| Set in Render → Environment | Or else |
|---|---|
| `KHAPEE_OWNER_EMAILS` | "Every restaurant" stays off |
| `SMTP_HOST` / `PORT` / `USER` / `PASS` | **No order email ever sends.** Free with a Gmail app password |
| `KHAPEE_SECRET` | Everyone is signed out each time the site sleeps |

### Alternate routes, most reliable first

1. **Email.** Survives everything — the address comes back with the snapshot,
   a push subscription does not.
2. **Push.** Self-heals whenever a dashboard is open; an order arriving after a
   sleep with every dashboard shut reaches nothing.
3. **The dashboard's own chime and notification row.** Works only while
   somebody is looking at it.

If push misbehaves on one particular phone, add that phone through the
alert-invite link instead — a separate subscription path.

## 4. Making menu data permanent

The free plan has no disk. The database is rebuilt from `data/snapshot.db`
every time the service wakes, so anything written at runtime is lost.

### The three free routes

1. **The committed snapshot is the durable store.** `npm run snapshot && git
   add -A && git commit && git push`. It survives everything because it is
   version control. The cost is that it is a manual step.
2. **Keep the service awake** and the rebuild stops happening at all. A free
   pinger — cron-job.org, UptimeRobot — on `/api/health` every 10 minutes.
   Runtime writes then persist between customers.
3. **A Petpooja menu self-heals.** They push on every menu edit, so it comes
   back on their next change.

### What is lost today without those

Menu edits made on the live dashboard, and Petpooja links created at runtime.

### Caveat worth checking

A free Render service is capped at a monthly pool of instance-hours, and one
kept awake all month spends nearly all of it. **This was not verified** — the
container doing this work cannot reach render.com. Confirm the current
allowance covers a 31-day month (744 hours). If it does not, run the pinger
during opening hours only; for a restaurant the effect is the same.

### Last resort

`plan: starter` in `render.yaml` plus the two commented disk blocks. Four
uncommented lines, and every problem in this section disappears at once.

## What to do, in order

**You**

1. Set `KHAPEE_SECRET`, `KHAPEE_OWNER_EMAILS` and the `SMTP_*` values in Render.
2. Add a free uptime pinger on `https://khapee.com/api/health`.
3. Send the Petpooja reply in `docs/petpooja-reply-2.md` — it gates everything
   in section 1.

## Notes for whoever runs the tests

- **Always `npm run build` before `npm test`.** Sixteen SEO tests fail
  otherwise; those routes only register when `dist/index.html` exists. With a
  build present the suite is 968 passed, 0 failed.
- The harness orphans its server on port 4399 when a run crashes. The next run
  then reports a misleading "no such table: users". Clear it first:
  `pkill -9 -f "server/index.ts"; rm -f data/test.db*`.
